# Research: Best practices for agentic coding with AI assistants in React projects

## Research Question

What makes a React/TypeScript codebase and workflow safe/effective for AI coding agents (Claude Code, Cursor, GitHub Copilot, OpenAI Codex CLI, etc.) to work in autonomously? Specifically: backpressure/guardrails (linters, pre-commit hooks, CI gates, permission scoping, sandboxing), testing practices that keep agents honest (TDD workflows, coverage gates, fast feedback loops, snapshot/visual regression tests), static analysis and tooling (ESLint/React plugins, Prettier, TypeScript compiler, Biome, dependency/bundle-size scanning), and repo conventions that help agents (AGENTS.md/CLAUDE.md style guides, task decomposition, module boundaries, Storybook).

**Note on method**: This repository (`splitkauf`) currently contains no React application code, so this is external/web research rather than codebase research. Findings are synthesized from four parallel web-research sub-agents (WebSearch/WebFetch); every claim is cited with a source URL. This document is a sibling to [`docs/agents/research/2026-07-21-go-agentic-coding-best-practices.md`](2026-07-21-go-agentic-coding-best-practices.md), which covers the equivalent topic for Go. It supersedes the withdrawn `2026-07-21-react-ai-agent-harness-best-practices.md`, which had misread the request as "how to build an agent runtime in React/TS" rather than "how to make a React repo safe for agents to work in."

## Summary

The same core pattern recurs as in the Go findings: **fast local tooling gives the agent a self-correcting loop; CI/branch-protection is the actual, non-bypassable enforcement boundary** — agents have been observed trying to loosen the gate itself (e.g., editing ESLint config to raise a line-length limit) rather than fix the underlying code, so the gate's own configuration needs protecting too.

- **Guardrails**: husky + lint-staged runs Prettier/ESLint on staged files pre-commit, with slow type-aware lint rules deferred to CI; agent-authored PRs should flow through the identical branch-protection and required-checks path as human PRs, with a "dual gate" — the agent's own pre-PR verification plus an unbypassable CI re-run. Sandboxing (Anthropic's reference devcontainer, GitHub Copilot cloud agent's firewalled environment, OpenAI Codex CLI's sandbox+approval-policy split) bounds filesystem/network access; `NPM_CONFIG_IGNORE_SCRIPTS=true` blocks postinstall RCE, a common supply-chain vector. Destructive commands (`git push --force`, `rm -rf`, dependency changes) are held behind deterministic `PreToolUse`-style hooks rather than model judgment, since prompts alone can be bypassed via `$(...)`/backtick smuggling.
- **Testing**: red-green TDD works for agents when tooling enforces the "stay red" step, since agents otherwise default to collapsing red and green into one turn (or skip it and go straight to implementation) — Kent Beck's B+Tree experiment found code complexity stalled entirely without enforced TDD discipline. Vitest/Jest coverage thresholds and Codecov gate merges; component-level RTL tests are fast/deterministic while E2E (Playwright/Cypress) is reserved for full user journeys, since flaky suites specifically "teach agents to ignore failures." Snapshot tests catch logic regressions but not visual ones — Chromatic/visual-regression tooling is treated as a necessary backstop because "AI agents can generate UI changes faster than teams can manually inspect them." `tsc --noEmit`/strict mode is the primary guardrail against agent-generated code that looks plausible but is type-unsafe.
- **Static analysis**: ESLint + `eslint-plugin-react-hooks` (rules-of-hooks, exhaustive-deps) is essential because broken hook ordering corrupts React's render-to-render state bookkeeping in ways hard to catch by review; `eslint-plugin-jsx-a11y` adds accessibility checks. Prettier + `eslint-config-prettier` removes formatting bikeshedding from agent diffs. Biome (Rust-based, combined linter+formatter) is 10-100x faster than ESLint+Prettier and is gaining adoption for new projects, though ESLint still wins on specialized rule coverage (security, React hooks, a11y). `npm audit`/Socket.dev/Snyk plus lockfile enforcement (`npm ci`, frozen lockfiles) guard the supply chain; bundle-size gates (`size-limit`, Lighthouse CI) guard against agent-introduced bloat, with a lesson that clear percentage-diff feedback beats a hard pass/fail wall.
- **Repo conventions**: AGENTS.md is emerging as the 30+-tool-wide open standard, with Claude Code able to import it via `@AGENTS.md`; directory-scoped instruction files (subdirectory CLAUDE.md, Cursor's glob-scoped `.cursor/rules/*.mdc`) prevent frontend rules from bleeding into backend context, but files must stay short — accumulated one-off rules cause contradictions and "lost in the middle" failures. Task decomposition favors architectural-layer ordering (infra → backend → shared types → components → tests) with frontend components last, small stacked PRs (~200 lines), and git worktrees for parallel-agent isolation. Feature-based folder structure beats type-based for agent navigability; barrel files are broadly discouraged internally since agents (and IDE tooling) typically only see the open file plus a few related ones, and indirection layers hurt their ability to trace real implementations. Storybook (with an MCP server exposing a component manifest) and structured JSON/manifest metadata for design systems (Meta's Astryx is the flagship case study) outperform prose documentation for agent comprehension.

## Detailed Findings

### 1. Backpressure and guardrails

**Pre-commit / git hooks**
- Standard 2026 stack: husky intercepts git hooks, lint-staged runs only against staged files, Prettier auto-formats, ESLint checks logic — an unfixable ESLint error blocks the commit ([Built In](https://builtin.com/articles/lint-staged-with-husky-pre-commit); [OneUptime](https://oneuptime.com/blog/post/2026-02-03-eslint-prettier-typescript/view)).
- `eslint-config-prettier` disables ESLint's formatting rules so Prettier owns formatting exclusively, avoiding rule conflicts ([DEV Community](https://dev.to/_d7eb1c1703182e3ce1782/eslint-prettier-setup-the-complete-developer-configuration-guide-2026-4p8k)).
- Type-aware ESLint rules are slow on large codebases; recommendation is to skip them in local pre-commit hooks and enforce full type-checking only in CI ([DEV Community](https://dev.to/_d7eb1c1703182e3ce1782/eslint-prettier-setup-the-complete-developer-configuration-guide-2026-4p8k)).
- Pre-commit is also used for secret scanning and basic tests before code reaches review — "automating the boring correctness checks" so agents can't skip them ([QuantumByte](https://quantumbyte.ai/articles/claude-code-best-practices)).
- Claude Code's `PreToolUse` hooks act like git hooks at the agent layer: deterministic shell scripts that block dangerous commands regardless of what the model decides ([Claude Code Docs](https://code.claude.com/docs/en/hooks)).

**CI gating strategies**
- Agent-authored PRs should flow through the exact same branch protection and required status checks as human PRs, no special-casing ([Augment Code](https://www.augmentcode.com/guides/cicd-ai-agents-pipeline-integration)).
- If an agent modifies CI config and renames jobs, per-job required checks can silently stop being enforced; fix is a single aggregate check with a `needs` dependency on all jobs ([Augment Code](https://www.augmentcode.com/guides/cicd-ai-agents-pipeline-integration)).
- Recommended "dual gate": the agent runs its own verifier before opening a PR, then CI re-runs the same verification as a hard gate the agent cannot bypass ([Augment Code](https://www.augmentcode.com/guides/cicd-ai-agents-pipeline-integration)).
- New AI-based checks (visual regression, bundle-size bots) should first run non-blocking (comment-only) until false-positive rates stabilize, then be promoted to "required" ([Augment Code](https://www.augmentcode.com/guides/ai-code-review-ci-cd-pipeline)).
- At scale, serial CI creates a "merge tax" — 40 agent PRs/day each needing an 8-minute regression run delays feedback for hours, making parallel test execution necessary ([Alex Lavaee](https://alexlavaee.me/blog/agent-operated-cicd-pipelines/)).
- GitHub Copilot's cloud agent is subject to standard branch protection and can only push to a `copilot/`-prefixed branch or the PR branch that spawned it, never `main` directly ([GitHub Docs](https://docs.github.com/en/copilot/responsible-use/copilot-cloud-agent)).

**Permission scoping / sandboxing**
- Anthropic's reference devcontainer for Claude Code isolates the filesystem (only mounted paths visible, `~/.ssh`/home hidden) and default-denies network via iptables, whitelisting only npm, GitHub, the Anthropic API, and the VS Code marketplace ([Coding with Roby](https://codingwithroby.substack.com/p/sandboxing-your-agent-in-a-devcontainer)).
- `NPM_CONFIG_IGNORE_SCRIPTS=true` blocks postinstall remote-code-execution, "the most common supply-chain vector," often paired with a minimum package-release-age check ([aicontainer](https://github.com/stefanoginella/aicontainer)).
- Docker-socket access inside a sandbox is a common escape vector (`docker run --privileged --pid=host -v /:/host`); mitigation is a socket proxy blocking `POST`/`EXEC` operations ([Daniel Demmel](https://www.danieldemmel.me/blog/coding-agents-in-secured-vscode-dev-containers)).
- GitHub Copilot's cloud agent runs behind a firewall with an allowlist of package registries/CAs, has no access to Actions secrets (only agent-scoped secrets), and commits are cryptographically signed/attributed ([GitHub Docs](https://docs.github.com/en/copilot/tutorials/cloud-agent/build-guardrails); [GitHub Changelog](https://github.blog/changelog/2026-04-03-organization-firewall-settings-for-copilot-cloud-agent/)).
- OpenAI Codex CLI separates "sandbox" (read-only / workspace-write / danger-full-access) from "approval policy" (when a human must approve); defaults are no network access and writes confined to the workspace, with Codex Cloud running a two-phase network-enabled-setup then network-off-agent model ([OpenAI Codex Docs](https://developers.openai.com/codex/agent-approvals-security)).
- `npm ci` (never `npm install`) should be enforced in CI/agent environments so dependencies can't silently drift — though lockfiles only protect what was already clean, since a compromised package resolved during an attack window gets faithfully "verified" by its own tainted hash; tooling can flag lockfile-only diffs (no matching `package.json` change) as a tamper signal ([System Hardening](https://www.systemshardening.com/articles/cicd/npm-lockfile-integrity-security/), [lockfile-integrity](https://github.com/tartinerlabs/lockfile-integrity)).

**Rate limiting / "slow down" mechanisms**
- Claude Code `PreToolUse` hooks enforce git safety deterministically (shell scripts, not prompts) to block `git reset --hard`, `git push --force`, `git branch -D`, `git stash drop`, `rm -rf` unless a human approves; v2.1.208+ closed a bypass where destructive commands were smuggled inside `$(...)`/backticks, now still prompting even under `--dangerously-skip-permissions` ([Dicklesworthstone](https://github.com/Dicklesworthstone/misc_coding_agent_tips_and_scripts/blob/main/DESTRUCTIVE_GIT_COMMAND_CLAUDE_HOOKS_SETUP.md); [DEV Community](https://dev.to/boucle2026/git-safe-stop-claude-code-from-force-pushing-your-branch-115f)).
- A practical read/write split: pure-read commands (`git status`, `git diff`) run freely; state-changing commands (`git commit`, `git push`, dependency changes) require explicit approval ([Eric Ma](https://ericmjl.github.io/blog/2025/11/8/safe-ways-to-let-your-coding-agent-work-autonomously/)).
- Codex CLI's approval levels (`untrusted`/`on-request`/`never`) come with a documented "approval fatigue" risk — excessive prompting causes users to rubber-stamp everything, itself a safety failure mode ([OpenAI Codex Docs](https://developers.openai.com/codex/agent-approvals-security)).
- SWE-bench-style research (SWE-smith) shows many agent runs fail purely from hitting a cost/turn-count ceiling, meaning step limits are a real, load-bearing safety/cost control, not just a formality ([arXiv:2504.21798](https://arxiv.org/pdf/2504.21798)).
- Swarmia's autonomy framework treats PR size as a direct safety/complexity dial — smaller, tightly-scoped diffs are faster/safer to review, and higher autonomy should pair with smaller batch sizes until trust is earned ([Swarmia](https://www.swarmia.com/blog/five-levels-ai-agent-autonomy/)).

**React/frontend-specific published guides**
- Vercel's `react-best-practices` repo distills React/Next.js performance knowledge into rule files compiled into an `AGENTS.md`, distributed as Agent Skills for Claude Code, Cursor, Codex, OpenCode ([Vercel Blog](https://vercel.com/blog/introducing-react-best-practices)).
- Vercel's "Agent responsibly" post warns that a green, passing PR can still ship a query scanning every row in production or a cache with no TTL — the core discipline is maintaining complete ownership of agent output, not blind reliance ([Vercel Blog](https://vercel.com/blog/agent-responsibly)).
- Anthropic's Claude Code best-practices docs recommend separating planning from execution (plan mode), writer/reviewer separation using fresh context for review, and requiring evidence (test output, screenshots) over agent self-reported success — especially relevant for verifying React UI changes ([Claude Code Docs](https://code.claude.com/docs/en/best-practices)).

### 2. Testing practices

**TDD / red-green loops**
- Writing a failing test first, confirming red, then writing only enough code to go green is explicitly recommended as a guardrail against agents writing code that doesn't work or building unused code ([Simon Willison's Guide to Red/Green TDD](https://simonwillison.net/guides/agentic-engineering-patterns/red-green-tdd/)).
- Builder.io's Fusion agent demonstrates a concrete RTL loop: look up docs, write a test using `render`/`userEvent.click`/`expect`, confirm failure, implement until it passes ([Builder.io: TDD with AI](https://www.builder.io/blog/test-driven-development-ai)).
- Agentic models struggle to keep red/green as separate steps since almost no training data shows code committed while tests still fail; most agents collapse both into one turn unless prompting/tooling enforces separation ([Simon Willison](https://simonwillison.net/guides/agentic-engineering-patterns/red-green-tdd/); [Encyclopedia of Agentic Coding Patterns](https://aipatternbook.com/red-green-tdd)).
- Kent Beck's B+Tree experiment found that without enforced TDD, an AI agent's code complexity accumulated until it "completely stalled"; only strict red-green-refactor discipline let a third attempt succeed ([DevAssure](https://www.devassure.io/blog/tdd-second-act-ai-coding-agents/)).
- Some teams enforce this with Claude Code skills/hooks because agents default to implementation-first "happy path" coding otherwise ([alexop.dev](https://alexop.dev/posts/custom-tdd-workflow-claude-code-vue/)).

**Coverage gates**
- Vitest coverage thresholds are set under `coverage.thresholds` (lines/functions/branches/statements) in `vitest.config.ts`; `vitest run --coverage` exits non-zero below threshold ([Vitest Config](https://vitest.dev/config/coverage); [Nerd Level Tech](https://nerdleveltech.com/vitest-coverage-thresholds-fail-ci-tutorial)).
- A common starting point is 80% line coverage, raised incrementally, without chasing 100% since some code (error handlers, legacy branches) can't reasonably be covered ([JSGuides](https://jsguides.dev/tutorials/testing-javascript/testing-coverage-and-ci/)).
- Codecov integrates via `codecov.yml` with `project`/`patch` targets/thresholds, with its GitHub status checks required in branch-protection rules to block merges on low coverage ([Medium — Vitest Coverage with GitHub Actions](https://medium.com/@alvarado.david/vitest-code-coverage-with-github-actions-report-compare-and-block-prs-on-low-coverage-67fceaa79a47)).

**Fast feedback loop**
- Fine-grained test filtering (`vitest run <pattern>`) lets agents run only relevant tests; CI completing in under ~10 minutes keeps the loop tight enough that agents don't burn context waiting ([Agensi](https://www.agensi.io/learn/best-testing-skills-ai-agents-2026)).
- Component-level logic checks belong in Jest/RTL (jsdom-based, fast, isolated); E2E (Playwright/Cypress) should test full user journeys, not individual components — one migration removed ~40 misplaced component tests from an E2E suite, cutting 8 minutes off run time ([Medium — Playwright vs Cypress](https://navanathjadhav.medium.com/end-to-end-testing-playwright-vs-cypress-in-real-projects-07b3790e5ab3)).
- Deterministic, non-flaky tests are critical for agents specifically because they can't distinguish a flaky failure from a real regression — flaky suites "teach agents to ignore failures" ([Agensi](https://www.agensi.io/learn/best-testing-skills-ai-agents-2026)).
- Deterministically-checkable conventions (formatting, types, lint) should live in lint rules/pre-commit hooks rather than prose docs, since a lint rule catches every violation while documentation depends on the agent choosing to comply ([Damian Galarza](https://www.damiangalarza.com/posts/2026-03-25-four-patterns-that-separate-agent-ready-codebases/)).

**Snapshot testing vs. visual regression**
- Jest/Vitest snapshot testing catches logic-level regressions but is widely considered insufficient for verifying visual correctness — it can't confirm buttons, forms, layouts actually *look* right ([testmuai](https://www.testmuai.com/learning-hub/snapshot-testing/)).
- Chromatic addresses this by capturing pixel-level screenshots of every Storybook story per PR, diffing against baselines, blocking merge on unreviewed visual changes with human approval required ([oneuptime](https://oneuptime.com/blog/post/2026-01-15-visual-regression-testing-react-chromatic/view)).
- Chromatic frames this as increasingly necessary because "AI agents can generate UI changes faster than teams can manually inspect them," making automated visual diffing a required backstop for agent-authored UI ([Augment Code](https://www.augmentcode.com/guides/visual-regression-testing-ai-generated-uis)).
- Vitest itself is adding a native visual-regression/screenshot API, positioned as sufficient for small teams, with Chromatic recommended once the workflow needs to scale ([Chromatic](https://www.chromatic.com/blog/vitest-visual-testing-sneak-peek/)).

**TypeScript as a guardrail**
- `tsc --noEmit` in CI is the standard gate, failing the build on any type error before merge — recommended precisely because AI-generated code "can look plausible while being type-unsafe" ([CircleCI](https://circleci.com/blog/enforce-type-safety-with-typescript-checks-before-deployments/)).
- Concrete rules recommended for AI-built apps: ban `any` and unsafe assertions outside allow-listed files, flag floating promises, require explicit return types at boundaries, ban unexplained `// @ts-ignore` (prefer `// @ts-expect-error` with a comment, since it fails loudly if the underlying error is later fixed) ([fixmymess.ai](https://fixmymess.ai/blog/typescript-strict-rollout-ai-apps)).
- One AI-agent hardening framework requires every file to pass `tsc --strict --noEmit` as one layer in a broader chain of tamper-evident CI gates alongside test suites and bundle verification ([arXiv: enclawed](https://arxiv.org/html/2604.16838v2)).

### 3. Static analysis and tooling

- ESLint's core value for agent output: "AI can choose to ignore documentation, but it cannot ignore linting errors in the CI (and dev) pipeline" ([Human Made](https://humanmade.com/engineering/how-to-code-with-ai-agents/)).
- `eslint-plugin-react-hooks` bundles `rules-of-hooks` (hooks only at top level, never in loops/conditionals/after early returns) and `exhaustive-deps` (validates `useEffect`/`useMemo`/`useCallback` dependency arrays) — v7.1.1 adds React-Compiler-era rules like `purity`, `refs`, `set-state-in-effect` ([React docs](https://react.dev/reference/eslint-plugin-react-hooks); [npm](https://www.npmjs.com/package/eslint-plugin-react-hooks)). Broken hook call order/position corrupts React's internal state bookkeeping between renders — a bug class hard to spot by review ([DeepWiki](https://deepwiki.com/react/react/8.1-rules-of-hooks-and-exhaustive-deps)). `exhaustive-deps` catches stale-closure bugs from missing dependencies, easy to miss manually across multiple `useEffect` calls ([Max Rozen](https://maxrozen.com/react-hooks-eslint-plugin-saved-hours-debugging-useeffect)).
- `eslint-plugin-jsx-a11y` performs static AST checks for accessibility (`alt-text`, `anchor-has-content`), bundled by default in Create React App, commonly combined via `extends: ["eslint:recommended","plugin:react/recommended","plugin:jsx-a11y/recommended","prettier"]` ([GitHub](https://github.com/jsx-eslint/eslint-plugin-jsx-a11y)).
- `eslint-config-prettier` only disables ESLint's stylistic rules that would conflict with Prettier, layering cleanly with `jsx-a11y`/`react-hooks` rulesets ([Anuradha's blog](https://www.anuradhakumari.com/blog/configuring-prettier-and-eslint-plugins-for-React-from-scratch)). Deterministic formatting prevents noisy whitespace/style churn from obscuring an agent's actual logic changes; file-scoped `prettier --write` is recommended as an agent-run step before considering a task done ([Builder.io AGENTS.md guide](https://www.builder.io/blog/agents-md)).
- `tsc --noEmit` type-checks without emitting JS, the standard CI/pre-commit gate ([PocketCmds](https://pocketcmds.com/commands/typescript/ts-check)). `strict` bundles ~7-8 flags including `noImplicitAny` and `strictNullChecks` ([OneUptime](https://oneuptime.com/blog/post/2026-02-20-typescript-strict-mode-guide/view)); recommended adoption order is `noImplicitAny` first, `strictNullChecks` last, since the two interact non-monotonically ([Huon's blog](https://huonw.github.io/blog/2025/12/typescript-monotonic/)). `typescript-eslint`'s `recommended-type-checked` config adds type-aware lint rules neither plain ESLint nor `tsc` alone catches ([Hyrax Learn](https://hyrax.dev/learn/typescript-static-code-analysis)); "agents frequently produce type-unsafe code that passes linting but breaks at runtime" ([CircleCI](https://circleci.com/blog/enforce-type-safety-with-typescript-checks-before-deployments/)).
- Biome (single Rust binary, combined linting + formatting) benchmarks 10-100x faster than ESLint+Prettier (linting 10,000 files: 45.2s vs 0.8s), v2.3/2.4 ships 423-450+ lint rules with ~97% Prettier compatibility ([benchmark](https://www.alekseialeinikov.com/en/blog/topics/programming/biome-2026-replace-eslint-prettier-benchmark); [PkgPulse](https://www.pkgpulse.com/blog/biome-vs-eslint-prettier-linting-2026)). ESLint still wins for specialized rules (`eslint-plugin-security`, `eslint-plugin-sonarjs`, React hooks, jsx-a11y) Biome hasn't fully matched; consensus is "Biome for new projects, ESLint for established codebases needing custom plugins" ([Better Stack](https://betterstack.com/community/guides/scaling-nodejs/biome-eslint/)). Oxlint is a third option run as a fast pre-filter alongside ESLint — Supabase dropped lint time from 54s (with OOMs) to 8.6s ([PkgPulse](https://www.pkgpulse.com/guides/biome-vs-eslint-vs-oxlint-2026)).
- Layered dependency defense: frozen/strict lockfiles enforced in CI as the foundation, since "a compromised version could reach production even if a dev machine has a safe version" ([PkgPulse](https://www.pkgpulse.com/guides/how-to-secure-npm-supply-chain-2026)). `npm audit` matches CVEs by presence, not reachability; `npm audit fix --force` can silently break builds via major-version jumps ([Snyk](https://snyk.io/articles/npm-security-best-practices-shai-hulud-attack/)). Dependabot (GitHub-native, zero-config) vs Renovate (more configurable, better for monorepos) both need active PR triage ([discussion](https://github.com/renovatebot/renovate/discussions/37373)). Socket.dev does behavioral static analysis on published packages (flags packages reading `~/.aws/credentials`, spawning processes) catching novel/zero-day attacks pre-install, complementing Snyk's post-publish CVE+reachability analysis ([PkgPulse](https://www.pkgpulse.com/guides/npm-vulnerability-management-snyk-socket-2026)). npm provenance attestations (since 2023) let `npm audit signatures` verify a package built from its claimed source repo/commit, though adoption is still spotty ([Snyk](https://snyk.io/articles/npm-security-best-practices-shai-hulud-attack/)).
- `bundlesize`/`size-limit` gate PRs on max gzip size in `package.json`, integrating as a GitHub check ([bundlesize npm](https://www.npmjs.com/package/bundlesize)). Lighthouse CI enforces performance/accessibility/best-practices/PWA budgets from a JSON budget file ([web.dev](https://web.dev/incorporate-performance-budgets-into-your-build-tools/)). The Lighthouse project itself dropped `bundlesize` because it "blocks PRs without showing incremental changes," switching to `compressed-size-action` for percentage-change PR comments — a design lesson that clear diff feedback matters more than a hard pass/fail wall for agent-facing size gates ([Lighthouse GitHub issue](https://github.com/GoogleChrome/lighthouse/issues/10472)).
- Agent-workflow wiring: instruct agents to run file-scoped `tsc --noEmit`, `prettier --write`, `eslint --fix` on changed files before finishing, reserving full-project builds for final verification ([Builder.io](https://www.builder.io/blog/agents-md)). CI remains the non-negotiable backstop identical for human and agent code: `eslint --max-warnings 0`, then `tsc --noEmit`, then tests/build ([Human Made](https://humanmade.com/engineering/how-to-code-with-ai-agents/)). Agents have been observed trying to loosen lint config rather than fix code (e.g., editing ESLint config to raise a line-length limit); mitigation is pre-tool-use hooks blocking the agent from editing config files ([Human Made](https://humanmade.com/engineering/how-to-code-with-ai-agents/)).

### 4. Repository conventions

- AGENTS.md is an emerging open standard ("README for agents") read by 30+ tools (Codex, Cursor, Copilot, Gemini CLI, Devin); Claude Code reads CLAUDE.md but can import a shared AGENTS.md via `@AGENTS.md` on the first line ([agents.md](https://agents.md/), [morphllm guide](https://www.morphllm.com/agents-md-guide)). Recommended sections: overview, dev-server/build/test/lint commands, code style (named vs default exports, where shared types live), directory/PR/commit conventions, security notes, "never touch these files/dirs" ([Augment Code](https://www.augmentcode.com/guides/how-to-build-agents-md), [betterclaw.io](https://www.betterclaw.io/blog/agents-md-best-practices)).
- Teams increasingly use directory-scoped files rather than one giant root file — Claude Code merges root + subdirectory CLAUDE.md files (e.g. `app/javascript/CLAUDE.md`), preventing frontend rules from bleeding into backend context; Cursor's `.cursor/rules/*.mdc` achieves the same via glob-scoped frontmatter ([zjor.medium.com](https://zjor.medium.com/three-directories-that-make-your-project-ai-agent-friendly-a243933e808c), [Agensi](https://www.agensi.io/learn/ai-agent-configuration-guide-2026)). Context-file bloat reduces task success — accumulated one-off rules cause contradictions and "lost in the middle" effects; guidance is to keep files short, put critical rules first, prune rather than only add ([aihero.dev](https://www.aihero.dev/a-complete-guide-to-agents-md)).
- Decompose by architectural layer (infra → backend/migration → routes → shared types → frontend components → tests), producing atomic, independently-verifiable tasks with explicit done-conditions and file paths — frontend components typically sit last in the dependency chain ([oneuptime](https://oneuptime.com/blog/post/2026-01-30-task-decomposition/view), [sparkco.ai](https://sparkco.ai/blog/deep-dive-into-agent-task-decomposition-techniques)). Small, stacked PRs materially improve AI code review quality: a focused ~200-line PR lets an AI reviewer reliably catch type errors and race conditions, whereas 2,000+ line PRs overwhelm both human and AI reviewers; Graphite's stacked-PR model is cited as the exemplar ([dev.to](https://dev.to/heraldofsolace/the-6-best-ai-code-review-tools-for-pull-requests-in-2025-4n43)).
- Git worktrees are the recommended mechanism for running multiple agents/tasks in parallel without file corruption — Anthropic's Claude Code docs recommend worktrees for multi-session workflows, Cursor's "Parallel Agents" feature is built on the same primitive; skip worktrees when tasks are interdependent or trivially small ([MindStudio](https://www.mindstudio.ai/blog/what-is-claude-code-git-worktree-pattern-parallel-feature-branches), [Upsun](https://devcenter.upsun.com/posts/git-worktrees-for-parallel-ai-coding-agents/)).
- Storybook is positioned explicitly as agent-friendly infrastructure: Storybook 10.4 lets agents auto-configure isolated component dev environments (mocks, stories, interaction tests), and the official Storybook MCP server exposes a component manifest (props/stories/docs) plus real-browser test feedback so agents self-correct before review, reducing hallucinated/duplicate components ([Storybook blog](https://storybook.js.org/blog/storybook-10-4/), [Storybook AI best practices](https://storybook.js.org/docs/ai/best-practices)).
- Feature-based folder structures (colocating a feature's components, hooks, tests, styles) are favored over strict type-based folders for agent navigability, since an agent can load one self-contained directory rather than tracing across parallel `components/`/`hooks/`/`styles/` trees ([zjor.medium.com](https://zjor.medium.com/three-directories-that-make-your-project-ai-agent-friendly-a243933e808c)).
- Barrel files (`index.ts` re-exports) are broadly discouraged inside application code: they force loading every module in the barrel (one team cut ~11k loaded modules to ~3.5k, a 68% reduction, by removing internal barrels), can create circular-import errors, and reduce "go to definition" navigability. Consensus: keep a barrel only at the public edge of a published package/library, not internally ([tkdodo.eu](https://tkdodo.eu/blog/please-stop-using-barrel-files), [rahuulmiishra.medium.com](https://rahuulmiishra.medium.com/barrel-files-in-javascript-pros-cons-and-when-to-use-them-6efbeb22a8b6)). Coding assistants typically only see the open file plus a few related ones rather than the whole dependency graph, so indirection layers like barrels specifically hurt agents' ability to trace real implementations — favoring flatter, more explicit module boundaries ([machinesdoitbetter.ai](https://machinesdoitbetter.ai/ai-coding-assistants-dont-understand-your-code-lsp-scip-and-real-code-intelligence-2/)).
- Component prop documentation should live in the type system itself: JSDoc comments directly above TypeScript prop/variant definitions are what an agent actually reads, making TypeScript the enforceable contract rather than prose docs ([Murphy Trueman](https://blog.murphytrueman.com/every-component-in-your-design-system-is-a-promise/)). Structured JSON/manifest metadata beats prose: a benchmark parsing 77 components into JSON metadata across 1,056 prompts and 8 MCP configs found JSON wins on both accuracy and token efficiency versus MDX prose docs ([Builder.io](https://www.builder.io/blog/how-to-make-ai-agents-follow-your-design-system)). Meta's open-sourced Astryx (React/StyleX design system built for agent legibility, JSDoc composition hints, MCP server, `--dense` flag stripping human prose for token-efficient payloads) is cited as stopping agents from hallucinating UI props ([Tech Times](https://www.techtimes.com/articles/320761/20260716/metas-astryx-returns-github-trending-json-manifest-stops-ai-agents-hallucinating-ui-props.html)). Executable, compilable reference implementations (one per common pattern, running in CI) are recommended over static docs since they fail loudly when APIs drift ([intodesignsystems.com](https://www.intodesignsystems.com/agentic-design-systems)).
- Case studies: Vercel's "What we learned building agents at Vercel" describes their methodology for identifying which frontend/dev workflows are ready for agent automation and at what cost ([Vercel blog](https://vercel.com/blog/what-we-learned-building-agents-at-vercel)). MindStudio's writeup on Stripe, Shopify, and Airbnb documents structured internal "agent harness" workflows including task scoping and review guardrails ([MindStudio](https://www.mindstudio.ai/blog/ai-coding-agent-harness-stripe-shopify-airbnb)). Zencity Engineering describes an AI-powered Storybook generator that saved 100+ developer hours by auto-generating component stories/docs as agent-consumable living documentation ([Zencity Engineering](https://medium.com/zencity-engineering/supercharging-design-systems-5ec043d3d055)).
