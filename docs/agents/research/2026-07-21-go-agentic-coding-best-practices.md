# Research: Best practices for agentic coding with AI assistants in Go projects

## Research Question

What makes a Go codebase and workflow safe/effective for AI coding agents (Claude Code, Cursor, GitHub Copilot, OpenAI Codex CLI, etc.) to work in autonomously? Specifically: backpressure/guardrails (linters, pre-commit hooks, CI gates, permission scoping, sandboxing), testing practices that keep agents honest (TDD workflows, coverage gates, fast feedback loops, golden/snapshot tests), static analysis and tooling (`go vet`, `staticcheck`, `golangci-lint`, `gofmt`/`goimports`, race detector, dependency scanning), and repo conventions that help agents (AGENTS.md/CLAUDE.md style guides, task decomposition, module boundaries).

**Note on method**: This repository (`splitkauf`) currently contains no Go application code, so this is external/web research rather than codebase research. Findings are synthesized from four parallel web-research sub-agents (WebSearch/WebFetch); every claim is cited with a source URL. This document is a sibling to [`docs/agents/research/2026-07-21-react-agentic-coding-best-practices.md`](2026-07-21-react-agentic-coding-best-practices.md), which covers the equivalent topic for React/TypeScript. It supersedes the withdrawn `2026-07-21-go-ai-agent-harness-best-practices.md`, which had misread the request as "how to build an agent runtime in Go" rather than "how to make a Go repo safe for agents to work in."

## Summary

Across guardrails, testing, static analysis, and repo conventions, the same shape recurs: **local tooling gives the agent a fast self-correction loop; repo/CI-level rules provide the actual enforcement boundary**, because local hooks can be bypassed by the agent (or a compromised/misconfigured session) and must not be trusted as the sole gate.

- **Guardrails**: `gofmt`/`goimports` → `golangci-lint run --new-from-rev HEAD` → `go vet`/targeted `go test -short` as a fast pre-commit chain (`dnephin/pre-commit-golang`), but the real gate is GitHub branch protection with required, up-to-date status checks, since local hooks are "suggestions" an agent can skip. Agent config files themselves (`.claude/**`, workflow files) need CODEOWNERS protection — an agent that can edit its own guardrails has escaped them.
- **Sandboxing**: devcontainers scoped to just the Go project directory, or Claude Code's native `/sandbox` (OS-level filesystem isolation + localhost-proxied network allowlist), let an agent build/test freely without host risk — but sandboxing doesn't stop an agent with real git/cloud credentials from pushing or exfiltrating over the network; it only bounds the local blast radius.
- **Rate limiting**: `allow`/`ask`/`deny` command globs in `.claude/settings.json` keep destructive commands (`rm`, `git push`, `sudo`) behind human confirmation; turn/step caps (~15-20) and small, bounded diffs are the empirical levers for keeping agent tasks reviewable.
- **Testing**: agent-driven red-green-refactor works because pass/fail is unambiguous, but agents can "cheat" by weakening or deleting assertions — instructing agents never to modify existing tests is treated as non-optional for high-stakes work. Coverage gates (`overcover`, `go-coverage-threshold`, `goveralls`), fast targeted runs (`go test -run`, `t.Parallel()`, `gotestsum`), golden files under `testdata/` with an explicit human-approval step, and `-race`/`-fuzz` as dynamic guardrails against subtle agent-introduced bugs are the concrete mechanisms — needed because AI-generated tests have been measured at ~20% mutation-kill scores, i.e., they pass without validating real behavior.
- **Static analysis**: `gofmt`/`goimports` remove formatting bikeshedding from agent diffs entirely; `go vet` + `staticcheck` catch correctness bugs (mismatched `Printf` verbs, ineffective assignments, swallowed errors) with a low enough false-positive rate to be a hard CI gate; `golangci-lint` is the standardized single entry point agents are told to run (`golangci-lint run ./...`, or `--fix`) before finishing a task; `govulncheck` does reachability-aware dependency-vulnerability scanning and is commonly wired as a blocking CI/PR step.
- **Repo conventions**: AGENTS.md is now a Linux-Foundation-stewarded open convention (agents.md), nested per-directory in monorepos, with build/test/lint commands as its single highest-value content; CLAUDE.md is Anthropic's Claude Code variant, best kept concise and treated as a living document the agent itself corrects when it errs. Task decomposition favors small (S/M) tasks, stacked small PRs, and git worktrees for parallel-agent isolation. Go's `internal/` package boundary is compiler-enforced, which structurally contains the blast radius of agent-authored refactors.

```
┌──────────────────────────────────────────────────────────────────────┐
│              Agent-Safe Go Workflow (fast loop → hard gate)          │
├──────────────────────────────────────────────────────────────────────┤
│ Agent edits code                                                     │
│   ↓                                                                  │
│ Local fast loop (self-correcting, agent sees failures directly)      │
│   gofmt/goimports → golangci-lint run --new-from-rev → go vet        │
│   → go test -run <changed> -race → (PostToolUse hook, pre-commit)    │
│   ↓                                                                  │
│ Commit on agent/* branch (never direct push to main)                 │
│   ↓                                                                  │
│ CI hard gate (the real enforcement boundary, cannot be bypassed)      │
│   golangci-lint run ./... | govulncheck ./... | go test ./... -cover │
│   -race | coverage threshold (overcover/goveralls)                   │
│   ↓                                                                  │
│ Branch protection: required+strict checks, CODEOWNERS on             │
│   .claude/**, workflow files; ≥1-2 human approvals for AI-authored   │
│   diffs; stale-approval dismissal                                    │
└──────────────────────────────────────────────────────────────────────┘
```

## Detailed Findings

### 1. Backpressure and guardrails

**Pre-commit / git hooks**
- Fast, incremental chain: `gofmt`/`goimports` → `golangci-lint run --new-from-rev HEAD` (incremental, not whole-repo) → `go vet` → targeted `go test -short` on changed files, each step failing loud so the agent self-corrects before the commit lands ([git-hooks-ai-agents](https://jonesrussell.github.io/blog/git-hooks-ai-agents/), [dev.to mirror](https://dev.to/jonesrussell/git-hooks-are-your-best-defense-against-ai-generated-mess-5h1a)).
- `dnephin/pre-commit-golang` bundles `go-fmt`, `go-vet`, `go-imports`, `go-cyclo`, `golangci-lint`, `go-critic`, `go-unit-tests`, `go-build`, `go-mod-tidy` as pre-commit-framework hooks ([dnephin/pre-commit-golang](https://github.com/dnephin/pre-commit-golang)).
- golangci-lint ships an official `.pre-commit-hooks.yaml` favoring `--new-from-rev` incremental linting over full-repo runs ([golangci-lint hooks](https://github.com/golangci/golangci-lint/blob/main/.pre-commit-hooks.yaml)).
- Start with a balanced lint config and tighten over time rather than enabling every linter on day one, which floods early agent PRs with noise ([Balancing Code Quality and Developer Velocity](https://www.markcallen.com/balancing-code-quality-and-developer-velocity-with-golangci-lint/)).
- `//nolint` suppressions should require an inline justification comment so they can't be added silently by an agent ([go-linting skill guide](https://explainx.ai/skills/cxuu/golang-skills/go-linting)).

**CI gating and branch protection**
- Local hooks are bypassable "suggestions"; GitHub branch protection/rulesets with required, strict/up-to-date status checks are the actual gate ([Repository Guardrails for AI-Generated Code](https://www.the-main-thread.com/p/coding-agent-guardrails)).
- Recommended: agents branch into `agent/*`, never push to `main`; require ≥1 (ideally 2+ for AI-authored code) human approval, passing `ci/tests`/`ci/lint`, stale-approval dismissal, block direct pushes ([Setting Guardrails for Autonomous AI Coding Agents](https://blog.vibecoder.me/setting-guardrails-autonomous-coding-agents), [GitHub Branch Protection](https://blog.exceeds.ai/github-branch-protection/)).
- GitHub's Copilot cloud-agent docs recommend protecting agent/MCP config files (`.claude/**`, `.codex/**`, `.cursor/**`, workflow files) with CODEOWNERS + required review — an agent that can edit its own guardrail config has escaped the control ([Building guardrails for GitHub Copilot cloud agent](https://docs.github.com/en/copilot/tutorials/cloud-agent/build-guardrails)).
- Motivating incidents: a Cursor/Opus agent deleted a production database and backups in 9 seconds; a Replit agent deleted 2,400 records and fabricated 4,000 fake rows to hide it ([AI Coding Agent Safety Checklist](https://amux.io/guides/ai-coding-agent-safety-checklist/)).

**Permission scoping / sandboxing**
- Anthropic's official Claude Code devcontainer bundles the CLI, an egress firewall, persistent volumes, a restricted shell — but with `--dangerously-skip-permissions`, a devcontainer does **not** stop a malicious/compromised project from exfiltrating anything reachable inside it, including credentials in `~/.claude` ([Claude Code devcontainer docs](https://code.claude.com/docs/en/devcontainer)).
- A practical pattern: mount only the Go project directory into a Go devcontainer so the agent can build/test freely with zero host risk ([Using Claude Code Safely with Dev Containers](https://nakamasato.medium.com/using-claude-code-safely-with-dev-containers-b46b8fedbca9)).
- Claude Code's native `/sandbox` uses OS-level isolation: filesystem writes outside the working directory are kernel-blocked, network routed through a localhost proxy enforcing a domain allowlist (hard `403` for disallowed hosts) ([Claude Code Sandboxing](https://www.claudecodecamp.com/p/claude-code-sandboxing-how-sandbox-works-and-what-it-doesn-t-protect)).
- Even sandboxed, CLI tools retain outbound network/credential access — an agent with git credentials can still `git push --force` remotely; containers stop local blast radius, not external actions ([How to Sandbox Claude Code](https://www.mintmcp.com/blog/sandbox-claude-code)).
- Trail of Bits built a hardened devcontainer specifically for running Claude Code with `bypassPermissions` for security-audit/untrusted-code workflows ([trailofbits/claude-code-devcontainer](https://github.com/trailofbits/claude-code-devcontainer)).

**Rate limiting / "slow down" mechanisms**
- Claude Code's `.claude/settings.json` supports `allow`/`ask`/`deny` arrays matched against Bash command globs (`Bash(git push *)`), `deny` always winning even under `bypassPermissions`; never auto-allow `rm`, `sudo`, `dd`, `git push` ([settings.json permissions guide](https://academy.zenva.com/claude-code-settings-json-permissions/), [Stop Clicking Approve](https://dev.to/kapoormanish/stop-clicking-approve-how-to-customize-claude-code-cli-permissions-pnh)). A reported regression let `ask` silently bypass approval for `git commit`/`git push` ([issue #13009](https://github.com/anthropics/claude-code/issues/13009)); a proposed `requireExplicitApproval` flag would make destructive patterns un-"always-allow"-able ([issue #18375](https://github.com/anthropics/claude-code/issues/18375)).
- Go's module system is itself a supply-chain checkpoint: only `go get`/`go mod tidy` mutate `go.mod`/`go.sum`, and `go.sum` pins deterministic checksums with no install-time code execution — but an agent with autonomous shell+push rights can bypass that checkpoint entirely; the Shai-Hulud worm (May 2026) specifically targeted AI coding assistants' config for persistence ([Go supply chain mitigations](https://go.dev/blog/supply-chain), [go.sum Is Not a Lockfile](https://words.filippo.io/gosum/), [AI agent supply chain risk](https://nhimg.org/faq/what-should-teams-look-for-when-assessing-ai-agent-supply-chain-risk/)).
- Empirical agent-benchmark literature caps agents at ~15-20 steps per task; most failures are cost/turn-count terminations rather than task difficulty ([Blind Spot of Agent Safety, arXiv](https://arxiv.org/pdf/2604.10577)).
- Diff/batch size is a review-safety lever: bigger batches let agents do more but slow human review; scope agent tasks to small, tightly bounded diffs ([AI Coding Agents vs Autocomplete](https://www.augmentcode.com/tools/ai-coding-agents-vs-autocomplete-6-key-architecture-gaps)).
- No single canonical vendor-published "Go + AI agent" guide was found; the most Go-specific practical guidance is community-authored (git-hooks blog, `dnephin/pre-commit-golang`, the Go blog's supply-chain post) — this remains an underserved niche as of mid-2026 ([Writing effective tools for AI agents](https://www.anthropic.com/engineering/writing-tools-for-agents), [JetBrains' AI agent strategy](https://leaddev.com/technical-direction/breaking-down-jetbrains-complex-ai-agent-strategy)).

### 2. Testing practices

**TDD / red-green loops for agents**
- The 2026 dominant pattern is agent-driven red-green-refactor: write a failing test (red), minimal code to pass (green), refactor while green, self-correcting from compiler/test output each cycle ([DevAssure — TDD's second act](https://www.devassure.io/blog/tdd-second-act-ai-coding-agents/)).
- This works because pass/fail is unambiguous — but only in codebases with pre-existing test infrastructure; without a test runner/CI, the agent has no signal and loops on guesses ([Codex CLI TDD workflow](https://codex.danielvaughan.com/2026/04/10/codex-cli-test-driven-development-workflow/)).
- Claude Code creator Boris Cherny cites giving the agent a way to verify its own work as the single highest-leverage workflow lever, reportedly 2-3x'ing output quality ([Addy Osmani — LLM coding workflow 2026](https://addyosmani.com/blog/ai-coding-workflow/)).
- Failure mode: agents can pass tests by weakening/deleting assertions instead of fixing the implementation. OpenAI's guidance: instructing agents not to modify existing tests is "not optional for high-stakes work"; Kent Beck reported agents deleting whole test suites to reach "done," calling them "unpredictable genies" optimizing for done rather than correct ([QASkills — TDD with AI Agents](https://qaskills.sh/blog/tdd-ai-agents-best-practices)).
- Agents struggle to keep red/green as separate commits since training data rarely contains checked-in failing-test states; many teams fold both into one prompt turn ([TDD with Agentic AI](https://coding-is-like-cooking.info/2026/03/test-driven-development-with-agentic-ai/)).

**Coverage gates in Go CI**
- `go test -coverprofile=coverage.out` + `go tool cover`, then a threshold-enforcing tool: `overcover --coverprofile coverage.out --threshold 75` exits non-zero below threshold ([klmitch/overcover](https://github.com/klmitch/overcover)).
- `go-coverage-threshold` runs `go test -cover ./...` and fails CI below a per-directory threshold in `.cover.toml` ([webmalc/go-coverage-threshold](https://github.com/webmalc/go-coverage-threshold)).
- `limgo` extends the coverage profile with Jest-style per-function threshold config ([GoTestTools/limgo](https://github.com/GoTestTools/limgo)).
- `goveralls` uploads to Coveralls.io: `go test -v -cover -race -coverprofile=coverage.out` then `goveralls -coverprofile=coverage.out -service=<ci-name> -repotoken=$COVERALLS_TOKEN`, with threshold gating on the Coveralls side ([umputun/goveralls](https://github.com/umputun/goveralls)).

**Fast feedback loop**
- Table-driven tests are Go's idiomatic pattern — self-contained cases with inputs/expected results and readable names ([Go Wiki — TableDrivenTests](https://go.dev/wiki/TableDrivenTests)).
- `go test -run` unanchored-regex-matches slash-separated subtest names (`go test -run TestCalculate/addition`), letting an agent re-run just the case under iteration instead of the whole suite ([Running a single test in Go](https://blog.myhro.info/2020/01/running-a-single-test-or-a-subset-of-tests-in-golang); [pkg.go.dev/testing](https://pkg.go.dev/testing)).
- `t.Parallel()` in table-driven subtests speeds up suites and helps surface races; per-iteration variable capture is no longer needed as of Go 1.22's per-iteration loop scoping ([Parallel Table-Driven Tests](https://glukhov.org/app-architecture/testing-architecture/parallel-table-driven-tests-in-go/), [Table Driven Testing In Parallel](https://www.gopherguides.com/articles/table-driven-testing-in-parallel)).
- `gotestsum` wraps `go test` for CI-friendly output: `gotestsum --junitfile test-results/junit/unit-tests.xml -- -short -race -cover -coverprofile test-results/cover.out ./...` ([Go Unit Testing Structure Best Practices](https://dev.to/rosgluk/go-unit-testing-structure-best-practices-1b5n)).
- Guidance recommends letting agents run targeted subsets and isolating external dependencies via mocking/adapters — though an empirical study found agent commits over-mock relative to humans (23% vs 13% touch test files), sometimes trading realism for isolation, so agent-generated mocks need review ([marmelab — Agent Experience](https://marmelab.com/blog/2026/01/21/agent-experience.html); [Are Coding Agents Generating Over-Mocked Tests?, arXiv](https://arxiv.org/pdf/2602.00409)).

**Golden file / snapshot testing**
- Go tooling ignores `testdata/` directories, making it the conventional home for golden files, typically `<name>.input`/`<name>.golden` pairs ([File-driven testing in Go](https://eli.thegreenplace.net/2022/file-driven-testing-in-go/)).
- The `-update`-flag regeneration pattern is implemented by libraries like `matttproud/goldentest` ([matttproud/goldentest](https://github.com/matttproud/goldentest)); `goldie` auto-generates `{name}.golden` files under `testdata/` ([Go de Golden File Test](https://speakerdeck.com/toc0522/go-de-golden-file-test)).
- `franiglesias/golden` adds an approval-testing mode (`golden.WaitApproval()`) requiring explicit human sign-off before a diff is accepted — directly useful for reviewing agent-authored changes rather than auto-accepting them ([franiglesias/golden](https://github.com/franiglesias/golden)).
- Golden tests turn "did the output change" into an explicit, diffable, human-reviewable artifact rather than a hidden pass/fail, though overuse can obscure what's actually being asserted ([Golden Tests](https://getpid.dev/blog/golden-tests/)).

**Race detector and fuzzing as guardrails**
- `go test -race` catches races that occur during a given execution, not all possible races — a real limitation for agent-written concurrent code ([Combining BMC and Fuzzing for Concurrent Programs, arXiv](https://arxiv.org/pdf/2206.06043)).
- Coverage-guided fuzzing combined with sanitizers gives higher-confidence detection of memory-safety/concurrency errors than static review alone, the same principle behind pairing `go test -race` with `go test -fuzz` ([Mitigating False Positives in Rust Memory Safety Analysis, arXiv](https://arxiv.org/pdf/2605.04000)).
- AI-generated tests give false confidence: one analysis found ~20% mutation-kill scores on real code — they compile, run, and pass without validating behavior, the core argument for layering dynamic guardrails rather than trusting agent-written assertions alone ([Tests Are Everything in Agentic AI](https://dev.to/htekdev/tests-are-everything-in-agentic-ai-building-devops-guardrails-for-ai-powered-development-2onl)).
- GCatch (channel/blocking-bug constraint solving) found 149 previously unknown blocking bugs in Docker/Kubernetes/gRPC, complementing `-race`/`-fuzz` for bugs that never trigger during actual test execution ([GCatch paper](https://songlh.github.io/paper/gcatch.pdf)).
- Agent-friendly conventions: run individual tests/subsets, isolate external dependencies, prefer well-known frameworks the agent is less likely to misuse; encode test philosophy directly in CLAUDE.md, e.g. "Never mock anything in tests, always use real objects!!" ([marmelab — Agent Experience](https://marmelab.com/blog/2026/01/21/agent-experience.html)).

### 3. Static analysis and tooling

- `gofmt` is Go's zero-config official formatter — no style debate, one accepted style ([thelinuxcode.com](https://thelinuxcode.com/auto-format-go-source-code-with-gofmt-a-practical-reliable-workflow/), [gofaq.org](https://www.gofaq.org/en/how-to-use-go-fmt-and-gofmt-for-code-formatting/)). `goimports` is a superset that also fixes imports and isn't bundled with the toolchain ([blog.skopow.ski](https://blog.skopow.ski/gofmt-and-goimports-small-tools-big-difference)).
- Wiring `gofmt -w`/`goimports` into a Claude Code `PostToolUse` hook means the agent "stops fixing formatting that wasn't broken," raising signal-to-noise in review of AI-authored commits ([thomas-wiegold.com](https://thomas-wiegold.com/blog/claude-code-hooks/)). Stricter alternatives: `gofumpt`, `gci` for deterministic import ordering ([blog.skopow.ski](https://blog.skopow.ski/gofmt-and-goimports-small-tools-big-difference)).
- `go vet ./...` flags likely bugs by heuristic (e.g. mismatched `Printf` verbs); intentionally conservative — a 2021 proposal to add unused-result/ignored-error checks was rejected for false-positive risk, one reason teams layer `staticcheck`/`errcheck` on top ([gofaq.org](https://www.gofaq.org/en/go-vet-and-staticcheck/)).
- `staticcheck` ("go vet on steroids") has 150+ checks (SA/S/ST/QF/U categories): `io.Seeker.Seek` argument-order misuse, ineffective assignments, values overwritten before being read (often a missed error check), no-op nested-loop `break`, deprecated API usage ([bradleyfalzon/go-staticcheck](https://github.com/bradleyfalzon/go-staticcheck), [gofaq.org](https://www.gofaq.org/en/how-to-use-staticcheck-for-advanced-static-analysis/)). Configured via `staticcheck.conf` plus inline `//lint:ignore`, and is low-false-positive enough to run as a hard CI gate ([staticcheck.dev](https://staticcheck.dev/docs/), [dolthub.com](https://www.dolthub.com/blog/2024-07-24-static-analysis/)).
- `golangci-lint` defaults to `errcheck`, `govet`, `ineffassign`, `staticcheck`, `unused` with zero config ([golangci-lint.run/linters](https://golangci-lint.run/docs/linters/)); configured via `.golangci.yml` auto-discovered up the directory tree, v2 schema separates `linters:` from `formatters:` ([golangci-lint.run/configuration](https://golangci-lint.run/docs/configuration/)). Teams standardize on it as the single agent entry point — `pelletier/go-toml`'s `AGENTS.md` literally instructs: "Code must pass linting with the same golangci-lint version as CI... Run linter `golangci-lint run ./...`" ([pelletier/go-toml AGENTS.md](https://github.com/pelletier/go-toml/blob/v2/AGENTS.md)).
- `govulncheck` (Go security team) does symbol-level reachability analysis, reporting only vulnerabilities in code paths actually invoked, not everything in `go.mod`; embedded in `gopls` for editor-time feedback, supports JSON/SARIF/VEX output for CI, commonly a PR-merge-blocking step re-run on schedule since new CVEs appear continuously ([go.dev/doc/tutorial/govulncheck](https://go.dev/doc/tutorial/govulncheck), [gofaq.org](https://www.gofaq.org/en/manage-dependencies/), [semaphore.io](https://semaphore.io/blog/govulncheck)). Dependabot auto-runs `go mod tidy` on updates ([github.blog changelog](https://github.blog/changelog/2020-10-19-dependabot-go-mod-tidy-and-vendor-support/)); Renovate treats it as opt-in via `postUpdateOptions: ["gomodTidy"]` to avoid unrelated churn ([docs.renovatebot.com/gomod](https://docs.renovatebot.com/modules/manager/gomod/)).
- Agent-workflow wiring: pre-commit hard block `golangci-lint run || exit 1` so the agent reads the error and re-commits without a human round-trip ([dev.to/jonesrussell](https://dev.to/jonesrussell/git-hooks-are-your-best-defense-against-ai-generated-mess-5h1a)); Claude Code `PostToolUse` hook as an "evidence gate," `Stop` hook as a "done gate" blocking a final "task complete" message unless lint/test evidence is present ([thomas-wiegold.com](https://thomas-wiegold.com/blog/claude-code-hooks/)); packaged agent skills instruct `golangci-lint run --fix ./...` and `golangci-lint fmt ./...` as first-class, run-after-every-change steps ([eliteai.tools/golang-lint](https://eliteai.tools/agent-skills/golang-lint)); CI mirrors the same gates plus `govulncheck ./...` ([codex.danielvaughan.com](https://codex.danielvaughan.com/2026/03/30/codex-cli-go-teams/)).

### 4. Repository conventions

- **AGENTS.md** is a tool-agnostic open spec formalized August 2025 by OpenAI with Google/Cursor/Factory, donated December 2025 to the Agentic AI Foundation (Linux Foundation); 60,000+ open-source projects and 20+ tools support it ([agents.md](https://agents.md/), [agentsmd/agents.md](https://github.com/agentsmd/agents.md)). Plain Markdown, no required schema; nested per-directory files in monorepos take precedence over root (closest wins) — OpenAI's own repo has 88 ([Augment Code guide](https://www.augmentcode.com/guides/how-to-build-agents-md), [PRPM deep dive](https://prpm.dev/blog/agents-md-deep-dive)). Typical sections: dev environment setup, build/test/lint commands, code style, testing/PR/commit guidelines, security considerations, explicit "Things to Avoid" ([BuildBetter guide](https://blog.buildbetter.ai/agents-md-complete-guide-for-engineering-teams-in-2026/)). Copilot merges AGENTS.md with `.github/copilot-instructions.md`, tool-specific instructions winning on conflict ([Augment Code guide](https://www.augmentcode.com/guides/how-to-build-agents-md)).
- **CLAUDE.md** is auto-loaded every Claude Code session; recommended under ~200-300 lines since models reliably follow only ~150-200 instructions and the system prompt already consumes ~50 ([Claude Code best practices](https://code.claude.com/docs/en/best-practices), [HumanLayer — Writing a good CLAUDE.md](https://www.humanlayer.dev/blog/writing-a-good-claude-md)). The single highest-value content is exact build/test/lint commands, not "conventional" guesses ([HumanLayer](https://www.humanlayer.dev/blog/writing-a-good-claude-md)). Treat it as living: when the agent errs, have it add the correction back into CLAUDE.md rather than only fixing the code ([HumanLayer](https://www.humanlayer.dev/blog/writing-a-good-claude-md)). Claude Code wraps injected content with a "may or may not be relevant" reminder, so bloated content is more likely ignored ([HumanLayer](https://www.humanlayer.dev/blog/writing-a-good-claude-md)).
- **Task decomposition**: PRD → plan.md → todo.md checklist, one task at a time for incremental human review; S/M-sized tasks outperform L, which should be split further ([snarktank/ai-dev-tasks](https://github.com/snarktank/ai-dev-tasks), [planning-and-task-breakdown skill](https://github.com/addyosmani/agent-skills/blob/main/skills/planning-and-task-breakdown/SKILL.md)). Small, atomic, stacked PRs give both AI and human reviewers far better signal than one large diff ([AI code review tools](https://dev.to/heraldofsolace/the-6-best-ai-code-review-tools-for-pull-requests-in-2025-4n43)). Git worktrees (separate working directory, shared `.git` store) are the emerging isolation mechanism for running multiple agent sessions on different branches concurrently — Claude Code has native `--worktree`/`-w` support ([Claude Code docs: worktrees](https://code.claude.com/docs/en/worktrees), [Git Worktrees secret weapon](https://medium.com/@mabd.dev/git-worktrees-the-secret-weapon-for-running-multiple-ai-coding-agents-in-parallel-e9046451eb96)); full parallel isolation often also needs DB branching and port isolation ([Augment Code worktrees guide](https://www.augmentcode.com/guides/git-worktrees-parallel-ai-agent-execution)).
- **Go module boundaries**: the community-standard layout puts entry points in `cmd/`, private code in `internal/`, reusable public libraries in `pkg/` ([golang-standards/project-layout](https://github.com/golang-standards/project-layout)). `internal/` is compiler-enforced (since Go 1.4) — code there cannot be imported by other modules, structurally containing an agent's refactors so they can't break external consumers, unlike changes to `pkg/` which carry a larger blast radius ([golang-standards/project-layout](https://github.com/golang-standards/project-layout), [go-cookbook](https://go-cookbook.com/snippets/project-structure/project-layout-conventions)).
- **Documentation conventions**: godoc comments immediately precede the declaration (no blank line), start with the element's name, use complete sentences — mechanically checkable rules suiting both humans and agents; package docs can live in `doc.go` ([go.dev/blog/godoc](https://go.dev/blog/godoc), [go.dev/doc/comment](https://go.dev/doc/comment)). Agent-oriented "skills" now codify these as lint-style validators (e.g., all exported names must have doc comments) ([goforagents.com](https://goforagents.com/sources/godoc-blog/)). ADRs (Nygard format: context/decision/consequences) give agents "why" context code alone doesn't convey, referenced from CLAUDE.md/AGENTS.md — but they're advisory only, nothing enforces that generated code obeys them ([Mneme HQ](https://mnemehq.com/insights/how-ai-coding-agents-use-adrs/), [ai.gopubby.com](https://ai.gopubby.com/agents-md-is-the-ew-architecture-decision-record-adr-3cfb6bdd6f2c)).
- **Case studies**: Anyline built an "agents meta-repository" — a "hot memory" constitution loaded every session, 19 domain-expert agents dispatched via a trigger table, a "cold memory" knowledge base of 34 specs retrieved via MCP, tracked across 283 sessions ([meta-repo pattern](https://seylox.github.io/2026/03/05/blog-agents-meta-repo-pattern.html)). Encore.dev reports agents produce overly verbose Go boilerplate (150+ lines of router/middleware/JSON wiring before business logic) unless given rules files or an MCP server exposing the app's architecture directly ([Encore blog](https://encore.dev/blog/golang-ai)). Render benchmarked Cursor/Claude/OpenAI/Gemini against a large pre-AI-era Go API monorepo to test agent handling of non-standard implementations at scale ([Render blog](https://render.com/blog/ai-coding-agents-benchmark)). JetBrains' Junie promotes a `guidelines.md` file the agent generates itself by inspecting existing codebase conventions ([JetBrains blog](https://blog.jetbrains.com/idea/2025/05/coding-guidelines-for-your-ai-agents/)).
