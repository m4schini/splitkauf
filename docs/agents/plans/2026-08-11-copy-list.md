# PLAN: Copy a shopping list (US-L.10)

Add a "Copy" action for shopping lists. Copying creates a new list containing
every non-deleted item of the source (open and checked alike), with every item
reset to unchecked. The API accepts an optional name; when absent the server
derives "«Original name» (copy)". In the UI a Copy button in the list-detail
header copies the list and navigates into the copy. The action is online-only.

## Acceptance Criteria

- A list can be copied via `POST /api/v1/lists/{listId}/copy` (authenticated),
  returning 201 with the new list summary.
- The copy contains every non-deleted item of the source (open and checked),
  each with `checked=false` and `checkedAt=null`; name, quantity, unit, and
  note are preserved; the copied items keep the source's display order.
- The request body is optional and may carry a `name`; when absent the server
  names the copy "«Original name» (copy)", trimmed (rune-safe) so the result
  fits the 200-character domain limit.
- Copying a missing list yields an RFC 9457 404 problem; an empty list copies
  to an empty list. A supplied empty name (`""`) is rejected by the OpenAPI
  validator (`minLength: 1`, generic validation problem); a whitespace-only
  name reaches the domain and yields a validation problem with a `/name`
  pointer — matching the behavior of the existing name-taking endpoints.
- The copy is created atomically (one transaction) and publishes a `lists` SSE
  hint so other clients refresh their overview.
- ListDetail's header shows a Copy button next to Rename/Delete; tapping it
  copies the list and navigates into the new copy. The action is online-only:
  while offline it fails with a visible, non-blocking error message.
- Documentation: new user story `US-L.10-copy-a-list.md`, story index updated,
  OpenAPI spec extended.

## Technical Key Decisions and Tradeoffs

1. **Copy scope — all non-deleted items, all unchecked:** the copy is a fresh
   version of the whole list.
   - Why: matches the requirement literally; "only open items" would be a
     different carry-over feature.
   - Impact: the repository copy filters `deleted_at IS NULL` and forces
     `checked=false, checked_at=NULL`.
2. **Naming — optional `name` in the request, server default "Name (copy)":**
   - Why: keeps the UI one-tap now; a naming prompt can be added later without
     an API change.
   - Impact: `CopyListRequest` with optional `name`; the domain derives and
     rune-safely trims the default so it fits `maxNameLength`.
3. **Server-side copy in one repository transaction:** new
   `Repository.CopyList` doing `INSERT lists` + `INSERT items … SELECT` inside
   `BeginTx` (the repository's first transaction).
   - Why: atomicity and a single round trip; the client never re-uploads items.
   - Impact: the repo re-verifies the source list inside the transaction with
     `SELECT … FOR KEY SHARE`, locking the source row so a concurrent
     `DeleteList` cannot commit mid-copy — a vanished source yields
     `ErrNotFound`, never a half or silently empty copy.
4. **Item order preserved via staggered `created_at`:** items are read in
   display order (`ORDER BY created_at, id`) and inserted with
   `created_at = now + row_number × 1µs`.
   - Why: a single shared timestamp would make the copy's order random (UUID
     tie-break); reusing the source's `created_at` would make copied items
     appear older than their list.
   - Impact: one window function in the copy statement; no schema change.
5. **UI placement — ListDetail header only; navigate into the copy:**
   - Why: overview rows stay uncluttered (mobile-first UX research §6); the
     user lands in the copy ready to rename or shop.
   - Impact: `ListDetail` gains an `onCopied(listId)` prop wired to the `App`
     view state; no changes to `ListsOverview` rows.
6. **Online-only (no outbox):** a plain `useMutation` without a registered
   `mutationKey`/defaults, so the copy is never queued or replayed offline.
   - Why: navigating into the copy needs the real server ID; offline copy
     would need temp-ID navigation and remapping — heavy machinery for v1.
   - Impact: no `registerMutationDefaults` entry; failures surface as an
     inline error message in ListDetail.

```
POST /api/v1/lists/{listId}/copy   body (optional): { "name": "…" }
        │ 201 → List (the copy, openItemCount = copied items, checked 0)
        ▼
V1.CopyList ──► Service.CopyList ──► Repository.CopyList (one tx)

                                             ├─ SELECT … FOR KEY SHARE (404 guard + lock)
```

## Abstractions and Code Reuse

Everything follows the existing spec-first vertical; the only new abstraction
is the repository's first transactional method.

- `splitkauf.openapi.yaml` — new path `/lists/{listId}/copy` (operationId
  `copyList`, tag `lists`), new `CopyListRequest` schema (optional `name`,
  `minLength: 1`); reuses `List`, `ListId`, `Problem`.
- `lists/`
  - `lists.go` — `Repository` gains `CopyList(ctx, sourceID uuid.UUID, name string) (List, error)`;
    new `copyListName(original string) string` helper (append " (copy)",
    rune-safe trim to `maxNameLength`).
  - `service.go` — `Service.CopyList(ctx, id uuid.UUID, name string) (List, error)`:
    load source via `repo.List` (404 + source name), validate a supplied name
    with `validateListName` or derive the default, delegate to `repo.CopyList`.
- `adapters/db/lists.go` — `CopyList` using `BeginTx`/`Commit` with a
  `defer tx.Rollback()`; maps no source row to `lists.ErrNotFound`.
- `ports/rest/v1/`
  - `api.go` — `ListService` interface gains `CopyList`.
  - `handlers_lists.go` — `CopyList` handler: tolerate an absent/empty body
    (the body is optional, so `decodeBody` cannot be used as-is on EOF),
    call the service, publish `events.TypeLists`, respond 201 `toList`.
- `frontend/src/`
  - `api.ts` — `CopyListRequest` type and `copyList(listId, body?)` helper.
  - `queries.ts` — `useCopyList(listId)`: plain `useMutation` (no
    `mutationKey`, not registered in `registerMutationDefaults`); on success
    prepend the returned list to the `listsKey` cache and invalidate.
  - `ListDetail.tsx` — new `onCopied: (listId: string) => void` prop; Copy
    button (disabled while pending) + inline error hint.
  - `App.tsx` — pass `onCopied={(id) => setView({ screen: 'list', listId: id })}`.
- `docs/user-stories/` — new `US-L.10-copy-a-list.md`; `README.md` index row.

## Logging & Observability

No new logging: repository/service errors bubble to `writeError`, which
already logs unhandled errors (`handlers_lists.go:256`) and emits RFC 9457
problems. The copy publishes the existing `events.TypeLists` SSE hint.

## Implementation Notes

- **`networkMode: 'offlineFirst'` + `retry: 0` on `useCopyList`** (not in the
  plan text): a plain `useMutation` inherits React Query's default `'online'`
  network mode, which *pauses* a mutation while offline instead of failing it.
  The copy would then sit pending forever with the button disabled and no
  message — the opposite of the "visible, non-blocking error" criterion.
  `offlineFirst` runs the fetch regardless, and with no retry the failure lands
  in the mutation's error state immediately. It still never enters the outbox:
  the hook has no `mutationKey` and no `registerMutationDefaults` entry, so
  nothing is persisted or replayed.
- The Copy button's error hint needs no separate state: React Query resets the
  mutation's error on the next `mutate`, so a retry clears the message.
- `Repository.CopyList` returns the new list's counts from the item insert's
  row count (every copied item is open by construction) rather than re-reading
  it via `r.List` — one round trip fewer, and the read would have to happen
  after the commit anyway.
- Adding the required `onCopied` prop touched every existing `ListDetail`
  render in `ListDetail.test.tsx` and `offlineOutbox.test.tsx` (a mechanical
  `onCopied={() => {}}`).
- Repository integration tests were run against a local Postgres 17 via
  `docker compose up postgres` + `go run . migrate` (colima was not running).
