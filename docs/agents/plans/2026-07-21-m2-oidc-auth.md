# PLAN: M2 — OIDC Authentication (BFF flow)

Replace the temporary dev-auth path (US-A.1) with a Backend-for-Frontend OIDC
Authorization Code + PKCE flow (US-A.2), transparent server-side token refresh
(US-A.3), server-side logout (US-A.4), and provider-derived group membership
(US-A.5).

Builds on the completed M1 slice
(`docs/agents/plans/2026-07-21-m1-lists-items-dev-auth.md`) and follows the OIDC
research (`docs/research/oidc-go-pwa-integration.md`).

## Product decisions (from the user)

1. **Dev-auth stays for local development.** OIDC is the *deployment* auth path,
   expected to run against **Authentik**. This deviates from US-A.2's literal "a
   dev provider is provisioned via compose": rather than shipping a compose OIDC
   provider, local dev keeps the hardcoded dev user. Recorded as a deviation.
2. **Config-driven mode selection (auto).** If an OIDC issuer + client id +
   client secret are configured, the backend runs the OIDC BFF flow; otherwise it
   falls back to dev-auth. No explicit mode toggle — deployment just sets the
   OIDC env vars.
3. **Sessions in Postgres** via `alexedwards/scs/v2` + `scs/postgresstore`
   (migration `000003`). No new infrastructure (no Redis), matching the
   one-command-deploy ethos (US-Q.3).
4. **Provider is Authentik**, a standard OIDC provider — the provider-agnostic
   `coreos/go-oidc/v3` + `golang.org/x/oauth2` stack is used (not the
   Zitadel-specific library).

## Acceptance Criteria

- **US-A.2**: In OIDC mode, `GET /api/auth/login` starts an Authorization Code +
  PKCE (S256) flow; the backend is the confidential client. The browser only ever
  receives an HttpOnly session cookie — no access/refresh/ID token reaches the
  frontend. `state` and `nonce` are validated on callback.
- **US-A.3**: `RequireAuth` refreshes the access token server-side via the
  refresh token when near expiry; rotated refresh tokens are persisted. An
  expired/revoked refresh token (`invalid_grant`) destroys the session and forces
  re-login.
- **US-A.4**: `POST /api/auth/logout` destroys the server-side session, clears the
  cookie, and (when the provider advertises `end_session_endpoint`) performs
  RP-initiated logout with `id_token_hint`.
- **US-A.5**: Every account that logs in is upserted into a `members` table keyed
  by the OIDC `sub`; there is no in-app membership administration. The dev user
  is also a member in dev-auth mode.
- Dev-auth mode is unchanged for local dev; `make check` is green.

## Design

### Endpoint surface

BFF auth endpoints are **browser-facing redirect endpoints**, not JSON API
resources, so they live at `/api/auth/*` (hand-written handlers mounted in
`ports/rest/server.go`), intentionally **outside** the versioned OpenAPI JSON API
and its request-validation middleware. This is a deliberate spec-first scoping
choice (US-Q.1): the OpenAPI document describes the JSON API; OAuth redirect
plumbing is not a JSON resource. The identity endpoint stays spec-first as
`GET /api/v1/me`.

| Method | Path | Purpose | Story |
|--------|------|---------|-------|
| GET  | `/api/auth/login`    | Start Authz Code + PKCE; redirect to IdP | US-A.2 |
| GET  | `/api/auth/callback` | Validate state/nonce, exchange code, create session | US-A.2 |
| POST | `/api/auth/logout`   | Destroy session; RP-initiated logout | US-A.4 |
| GET  | `/api/v1/me`         | Return `{id, name, email}` for the session/dev user | US-A.2/A.5 |

### Auth abstraction

A new `auth` package exposes an `Authenticator` interface with two
implementations selected by config:

- `devAuthenticator` — injects the hardcoded `DevUser` (M1 behaviour), and has
  no login/callback/logout (those return 404/redirect home).
- `oidcAuthenticator` — the BFF: `Login`, `Callback`, `Logout` handlers +
  `RequireAuth` middleware with token refresh, over an scs session manager.

Both expose the same `RequireAuth(next) http.Handler` middleware and a
`UserFrom(ctx)` helper, so `ports/rest/v1` reads the current user uniformly. The
existing `middleware.DevAuth`/`middleware.UserFrom` is migrated into this package
(or `auth` re-exports a compatible `UserFrom`) so `GetMe` and future handlers are
source-compatible.

### Session data (server-side only)

```go
type SessionData struct {
    AccessToken, RefreshToken, IDToken string
    Expiry  time.Time
    Subject, Email, Name string
}
```

Stored under one scs key as JSON; the cookie carries only the opaque session id.
Pre-login `state`/`nonce`/`pkce_verifier`/`return_to` are stored as separate scs
values and removed on callback. `RenewToken` is called after successful login
(session-fixation prevention).

### Membership (US-A.5)

A minimal `members` domain: table `members(subject PK, email, name, timestamps)`,
a repo `Upsert(ctx, Member)`. Called on every successful login (OIDC) and once at
startup for the dev user (dev mode). No API endpoint yet. Keeps M2 scope tight
while establishing the provider-as-source-of-truth principle.

## Deviations

- US-A.2 "a dev provider is provisioned via compose": per the user, local dev
  keeps dev-auth instead of a compose OIDC provider; OIDC targets Authentik in
  deployment. No OIDC container is added to compose.
- US-A.5 "every account known to the provider is a group member": realised via
  JIT provisioning (upsert on login). Enumerating *all* provider accounts before
  any login would require Authentik admin-API access and is out of M2 scope; the
  members table is populated as members sign in.
